# A/B/C 模型瓶颈诊断（2026-09-22）

## 决策

用 3 道开发诊断题 × 3 个条件 × 2 次重复 = 18 条轨迹，只改变"给模型多少辅助信息"，其余
（模型、prompt、工具、解码、步数、seed、容器）完全冻结。结果：

**定位能力和上下文获取确实弱，但它们不是当前的瓶颈。把"改哪个文件"和"那段代码长什么样"
直接交给模型之后，strict success 仍然是 0/6。真正的剩余差距是：模型在正确的位置写不出能编译、
语义正确的修改；以及在拿到位置之后无法从"读"推进到"改"。**

- **继续**：多步恢复/跳出拒绝循环这一方向值得继续做诊断（模型在 B 条件下 6/6 沦为拒绝循环，
  平均 21/24 步被拒，最长连续 23 步）；以及"更强模型 / 更简任务"的小规模对照。
- **暂停**：扩大当前 GRPO；以及 `swe_gym_sft` 里 locate 阶段的数据保真与 prompt 迭代那条线
  （v25–v29）。理由：这条线在优化"教模型搜到正确的字面量/文件"，而本轮证明把文件和源码直接
  给足后仍然 0/6 通过 —— 它瞄准的不是瓶颈。
- **仍不知道**：更大模型能否跨过语义门槛；B 的停滞有多少来自辅助消息的措辞；单题 2 次重复
  不能给出成功率，只能说这 18 条里一次都没成功。

## 4. 诊断指标：拒绝的原因比"拒绝"本身更有信息

`work/abc-diagnostic-20260922/summary.json` / `summary.md`，由
`scripts/summarize_diagnostic_probe.py` 从原始轨迹机械生成。

| 条件 | 步数 | 动作构成 | 被拒步数 | 拒绝分类 |
| --- | --- | --- | --- | --- |
| `A` | 143 | read 74、finish 22、search 20、run_tests 10、edit 14、list 3 | 71 | other 26、重复未变读 26、重复被拒动作 11、文本不匹配 3、编辑不可解析 3、未读先改 2 |
| `B` | 144 | **read 141**、search 1、list 1、finish 1 | **126** | **重复被拒动作 91**、重复未变读 33、other 2 |
| `C` | 124 | read 60、**edit 45**、finish 10、search 8、list 1 | 86 | 重复未变读 27、**编辑不可解析 21**、重复被拒动作 15、未读先改 10、文本不匹配 2 |

三件事在这里被分开：

1. **`B` 的问题不是"没找到"，而是"找到之后停住了"。** 7365 B r1 的第 1 步就读了
   `moto/dynamodb/models/dynamo_type.py`，随后 22 次重复同一个读取动作，每次都被
   `do not reread an unchanged file` 拒绝，最长连续 23 步，直到步数用尽。6/6 条 B 轨迹都是这个
   形状（被拒 20–23 步）。harness 的拒绝与升级提示是正确的，模型没能用它换一个动作。
2. **`C` 的问题不是"没找到位置"，而是"写不出能编译的修改"。** `C` 4/6 条编辑到了修复文件，
   45 次编辑尝试里 21 次被拒为"会让文件无法解析"（`IndentationError`），2 次文本不匹配。
   也就是说：位置和代码都摆在面前时，模型产出的是**语法无效**的补丁。
3. **`C` 的窗口不能替代真实读取。** 10 次拒绝是 `replace_lines requires reading the target file
   first` —— 我们没有绕过"编辑前必须读过"的约束，这也说明 C 的帮助是部分的（模型仍要自己读）。

搜索行为：`A` 6/6 条会搜自己观察里出现过的字面量（`update_item`、`Decimal`、`send_task_success`、
`waitForTaskToken`）；`B` 只有 1/6（它已经被点名，不需要搜）；没人去搜"答案文本"以外的取巧字面量。

## 5. 两处典型证据

**部分修复可观察，但收不了尾（7514，`A` r2 与 `C` r2，seed 170001）**：两条都应用了
`moto/s3/models.py` 的编辑，把 f2p 从 0/3 推到 **2/3**，没有引入任何 p2p 回归，剩下的永远是同一个

一步"的直接证据，也正是选 7514 的理由。

**改对文件却改坏全局（7514，`A` r1，seed 160001）**：应用了 `models.py` + `responses.py` 两处编辑，
f2p 0/3，**p2p 回归 7/7**（全部原本通过的测试被打破）。这条轨迹说明模型的编辑不是"没生效"，
而是"生效了但方向错误"——比 0 编辑更难被现有 harness 引导回正轨。

**改对文件、改错内容（7608 C r1/r2）**：两条都编辑了 `moto/stepfunctions/models.py`（gold 文件），
f2p 0/2；r2 有 12 次编辑被拒。它找到了文件，但没找到该改的位置和内容。

**锚点没有复现（7365）**：7365 是 v20 sweep 中这条 prompt 线唯一成功过一次的题，本轮 A/B 两臂
4 条轨迹**一次编辑都没应用**（1–2 次编辑被拒）。这与项目已记录的"8 个 seed 里只有 2 个可复现"
一致，也提醒不能把历史单次成功当作可达性保证。

## 6. 对五类假设的裁定

| 假设 | 裁定 | 依据 |
| --- | --- | --- |
| 1 定位实现文件能力不足 | **部分成立，但不是瓶颈** | `A` 只 2/6 编辑到修复文件；但 `B` 把定位变成 0 成本后仍然 0/6 通过 |
| 2 获取/利用源码上下文能力不足 | **部分成立** | 把上下文直接给出（`C`）确实把"不编辑"（`B` 0/6）变成"编辑"（4/6）；但改变的是是否尝试，不是是否正确 |
| 3 充分上下文下语义修复仍不足 | **成立，本轮最强证据** | `C` 0/6 strict、f2p 2/12，主要失败模式是编辑不可解析（21 次） |
| 4 多步执行、测试反馈与恢复不足 | **成立且独立** | `B` 6/6 沦为拒绝循环（平均 21/24 步被拒，最长 23 连击）；`A` 平均 3.17 次 finish 被拒 |
| 5 环境或评测缺陷使能力不可判断 | **本轮基本排除** | 18/18 无基础设施失败；三题 fail-before + gold pass-after 全部自检通过；新增 34 项测试在 Windows 与 VM 均通过 |

B 的辅助措辞里有 "Read them yourself before editing"，可能加重反复读取；每题只有 2 次重复。

## 9. 唯一建议优先执行的后续实验

**目的**：排除"样本太少 / 采样运气"这一解释，判断 14B 基座在**给定完整上下文**时到底能不能写出
一个能编译、且能推进 f2p 的修改。

**设计**：只跑 `C` 条件（oracle-context），3 题 × 8 次重复 = 24 条，seed 从 140001 起、与现有
C 条件同一 seed 区间；其余参数与本轮完全一致（同时保留现有 6 条 C 轨迹，`--resume` 可复用）。
额外记录：每次编辑尝试是否通过语法门（环境已把不可解析编辑拒绝，只需统计）、以及是否触达该题
剩余的 f2p 节点。

**预算**：约 40–60 分钟 GPU（本轮 18 条用了 23 分钟）。

**什么结果让我们停止**：若 24 条里仍然 0 strict，且新增解决的 f2p 节点不超过 2 个（即与现有
2/12 同量级），则判定"14B 基座在本任务族上的语义修复能力不足"这一结论成立 —— 停止在 14B 上
继续做 SFT/GRPO 与 locate 数据，转向"更强模型的小规模对照"或"更简任务"，并且不再投入任何
prompt/harness 侧的提示工程。反之若出现 ≥3 条应用了**可编译**编辑并推进 f2p，则恢复方向应当是

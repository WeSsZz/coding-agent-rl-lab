## 3. 截图五条简历模板应该怎样替换

### 3.1 数据与环境

截图的 2,438 是 SWE-Gym 数据集规模，不是我们处理完的任务数。我们固定准备的是同一 Moto 仓库的 10 个实例，6/2/2 是项目内部划分，不是官方 SWE-Bench 划分，更不是跨仓库泛化验证。

建议讲法：

> 我先限制任务规模，固定仓库快照、镜像、测试命令和数据划分，使失败可复现。每个 trial 用独立环境先验证原始故障，再让策略编辑源码，最后运行测试。gold patch 与 verifier 的私有配置不进入普通 policy task；只在训练监督和基础设施正对照中使用答案。

追问要点：test patch、gold patch、issue 是不同对象；容器启动失败也不能当成补丁语义失败；同仓库不同 Issue 的划分并不证明预训练无污染。当前模型能看到实际测试失败输出，因此不能声称“测试信息完全隐藏”；准确说法是私有答案字段不直接进入策略输入，测试文件受保护，实际 observation 按协议提供。

证据：[任务适配](../src/coding_agent_rl_lab/swe_gym.py)、[Docker 环境](../src/coding_agent_rl_lab/docker_environment.py)、[任务准备](../src/coding_agent_rl_lab/swe_gym_prepare.py)。

### 3.2 模型与 Agent

我们使用轻量受限 scaffold，不是 OpenHands；基础模型负责生成下一步动作，scaffold 负责解析、执行、返回 observation、预算与权限。7B 是主要 SFT/GRPO 实验模型，14B 用于导航及相关 SFT 对照；没有 32B 教师训练成果。vLLM 用于推理服务，首个训练入口使用 Transformers generation，不写“vLLM 加速训练”。

建议讲法：

> 我把模型能力和执行系统分开。模型每步输出严格工具动作，环境负责验证参数和执行工具。为了减少长轨迹中上下文膨胀、重复搜索和精确替换失败，我增加局部读取、共享 observation 预算、循环保护以及只允许编辑已读源码的行替换恢复动作。

不要把工具限制包装成通用编码平台；它是在受控训练实验中减少变量的选择，动作表达能力也受限制。所有工具动作、训练模板和推理协议必须一致，否则参数学到的格式未必能在 rollout 中运行。

证据：[模型策略](../src/coding_agent_rl_lab/model_policy.py)、[rollout](../src/coding_agent_rl_lab/rollout.py)、[协议诊断](moto-7607-diagnostic-v2-execution-20260917.md)。

### 3.3 SFT 与 GRPO

204 条是由 51 个源码 hunk 构造出的 locate/inspect/edit/verify 动作监督样本，不是 204 条模型自主完成的成功长轨迹。后续有真实状态重放和通过测试的教师恢复轨迹，也不能一概说成自主采集成功样本。

建议讲法：

> 早期基座模型在真实任务上奖励几乎全零，直接 GRPO 缺少组内可区分信号。我先做 train-only gold 动作监督，让模型学习工具协议，再接入环境交互式 GRPO。真实任务首次有效单步更新得到奖励 [0, 0.15] 和非零梯度，说明链路工作；由于 0.15 只代表有效编辑并执行测试，不能证明修复质量提高，所以继续做了冻结策略方向检查。

确切机制指标：该步 `reward_std=0.1061`、`grad_norm=0.4935`。用于回答“如何知道真的更新”，不建议把 grad norm 填成简历业务成果。我们接入 TRL，不是从零实现 GRPO 优化器；没有完成大规模拒绝采样训练或稳定多步 RL 增益验证。

证据：[SFT 数据](../src/coding_agent_rl_lab/swe_gym_sft.py)、[SFT 训练](../src/coding_agent_rl_lab/sft_train.py)、[GRPO 训练](../src/coding_agent_rl_lab/grpo_train.py)、[README 历史机制实验](../README.md)。

### 3.4 奖励与 Verifier

这里的 verifier 是**可执行测试验证器**，不是截图中训练出来的 Outcome Verifier。未完成候选成功概率模型、Best-of-N 排序或 verifier 校准，简历不写这些。

建议讲法：

> 我把训练奖励和最终成功指标分开。最终成功要求测试通过、存在源码补丁且无违规。训练可以提供部分奖励，但必须从真实环境读出。旧奖励给有效编辑加主动验证 0.15，即使引入新增失败也可能得分，配对实验暴露了这个缺口。我增加版本化 conservative-v2，让未知测试状态、新增失败和未验证补丁不能获得部分奖励。

v2 要先满足可比较 pytest 结果、有效已验证补丁且无新增失败；无改善只给 0.03，减少失败再增加 `0.25 × 减少比例 + 0.10`。严格成功为 1，违规为 -1。权重是工程设计，未通过充分消融证明最优。9 月 13 日文件说当时未部署，后续 9 月 14 日已用于实验判分；不能把旧文件状态当成现状。

这里最有价值的结论是“奖励上涨不等于能力提高”，而不是宣称观察到了经证实的蓄意 reward hacking。我们观察到了不良激励与错误补丁被给分，尚不足以解释模型主观策略。

证据：[奖励实现](../src/coding_agent_rl_lab/reward_shaping.py)、[配对方向检查](adapter-direction-check-20260913.md)、[v2 后续使用](train-failure-reduction-search-20260914.md)。

## 5. 最值得准备的三个技术故事

### 故事 A：为什么 reward 涨了，我反而停掉扩训

- 问题：单步 GRPO 已有效更新，但参数动了不等于修复更好。
- 实验：固定任务、种子与预算，SFT/GRPO 各 12 个 train trial 和 4 个 regression trial，共 32 条。
- 观察：train 有效补丁 3→5，旧平均奖励 0.0375→0.0625，但严格成功与测试改善均为零；新增失败样本 1→2。regression 有效补丁 1→0。
- 解释：旧奖励会奖励“做了编辑并测试”的行为，缺少足够的语义约束。小样本不足以宣称显著退化，但不足以支持扩大训练。
- 改进：版本化保守奖励，未知结果及新增失败不给部分分；后续完整 7514 上三条回归补丁均得零。
- 边界：证明已知激励缺口被限制，没有证明新奖励能提高成功率。

### 故事 B：怎么区分“找不到文件”和“不会修”

- 问题：任务失败可能发生在导航、动作格式、编辑执行或语义修复，单一最终成功率无法定位。
- 方法：先用前八次工具调用的目标源码到达率隔离导航，暂不混入完整修复；再从已读源码的 import/继承关系提供 parent implementation 路径，避免直接向模型注入 gold 文件答案。
- 观察：14B navigation adapter 的两组结果合计 1/8；加入 parent-path 协议后结果不稳定，继续用真实过渡样本监督后两组为 3/4 与 1/4，即 4/8。
- 下一层：完整 verifier 仍无改善，进入固定状态和编辑动作诊断；P2 adapter 在七个编辑前状态能应用四个编辑，但七个均没有立即测试改善。
- 边界：这些是单题、train 上的多因素探索，不能归因成“某一技巧普遍提升 37.5 个百分点”。局部编辑可能必须配合后续动作才产生效果，不能仅凭立即 verifier 就认定每个中间动作错误；9 月 18 日计划增加教师后缀正对照，但尚无完成结果。

### 故事 C：训练 loss 下降，为什么执行还是失败

- 问题：监督学习在 teacher forcing 下预测下一个 token，并不自动保证自由生成能完成工具链。
- 排查：比较训练与 rollout 工具 schema 和历史 tool_calls 渲染哈希，检查监督 token、mask 边界、截断与教师链完整性。
- 发现与修正：修复协议差异；完整教师链有 18 个动作，旧混合数据只选 12 个，缺少部分 search/read。P0 修复后 1,613 个监督 token 无全 mask、错位或截断问题。
- 结果：诊断 SFT 后目标动作 NLL 从 0.572 降至 0.291，但三个训练状态自由 rollout 仍 0/3 严格成功。随后七状态诊断出现三个特殊 token/不可解析响应和四个可应用但没有修复的编辑。
- 结论：优化目标确实被学习了一部分，仍未转化为稳定行为；不能只根据 loss 继续增加训练步数。当前尚未完成干净底座配对，不能把原因确定为 adapter 退化或模型规模不足。

## 6. 按截图各部分准备追问

以下区分“本项目事实”和“方法知识”。没有实现的部分可以说明设计思路，不使用过去完成时冒充经历。

### 数据：八个问题

1. **SWE-Gym 与 SWE-Bench？** 前者为训练软件工程 Agent 提供任务和可执行环境，后者常用于修复能力评测。本项目接入 SWE-Gym 小子集，没有完成 SWE-Bench 官方榜单评测。
2. **Issue 任务和 SFT 轨迹？** 任务定义问题、仓库与验证条件；轨迹是某个策略在任务上的动作和观察序列，一个任务可以产生多条轨迹。我们早期 SFT 是 gold hunk 派生的动作监督。
3. **358→11 个仓库？** 这是截图引用的上游数据构建叙述，不是我们的筛选成果。不要背成自己的工作；本项目实际是固定 Moto 子集。上游数量和筛选细节另按原论文核对。
4. **实例字段？** instance_id、problem_statement、repo、base_commit、version、patch、test_patch、FAIL_TO_PASS、PASS_TO_PASS；本项目还需要审计过的 test_command 和 provenance。
5. **Gold patch 的作用？** train-only 监督与基础设施正对照；模型评测不拿 gold 当输入，也不以补丁字符串完全相同作为正确性标准。
6. **怎么防污染？** 固定并校验任务划分，拒绝 regression/held-out 进入训练构建器，保存来源与哈希，答案轨迹和普通轨迹分离。只能说明显式数据边界，无法保证基础模型预训练从未见过相关代码或 Issue。
7. **F2P/P2P？** 应从失败变为通过的目标测试，以及应继续通过的原有测试。目标测试通过仍可能引入回归；当前实现还比较执行中解析出的失败标识，不能声称训练做了完整 F2P/P2P 权重消融。
8. **Docker 失败算模型失败？** 基础设施失败单列并保留记录。总体运行可靠性可计失败；模型能力指标要说明有效试验口径，不能静默删掉。由模型补丁导致测试超时或解析崩坏，还须与环境启动故障区别。

### 模型与 Agent：六个问题

1. **为什么 Qwen2.5-Coder？** 本项目选择可本地部署、可微调的代码模型，在可获得的单卡资源内建立基线；不声称做过全面选型或它是当前最优。
2. **7B/14B/32B？** 7B 主线训练，14B 导航及 SFT 对照；未使用 32B 建立该项目的教师体系。某个 14B 对照失败不足以排除模型容量因素。
3. **基础模型与 OpenHands？** 前者生成动作，后者是 Agent 框架；我们实际用了自定义受限 scaffold，没有接入 OpenHands。
4. **一条轨迹包含什么？** task/policy 版本、初始观察、逐步 action/observation、原始模型响应、采样信息、工具结果和最终测试/reward。API key 不进入轨迹。
5. **一定要先 SFT？** 不是理论必需；本项目因为协议和编辑表现弱、同组奖励常全零，先做工具监督是针对观察到的问题。好的基座若已有可区分的执行反馈，可直接尝试 RL。
6. **LoRA 影响能力吗？** 降低可训练参数和优化器状态开销，但不是无损承诺，也不消除激活显存；有可能改变行为分布或造成遗忘，需冻结前后对照。

### 训练算法：十个问题

1. **拒绝采样拒绝什么？** 通常按验证结果筛掉失败/不合格生成，保留通过的轨迹做 SFT；本项目有成功样本资格筛选，但未完成规模化 rejection-sampling 训练实验。
2. **RS-SFT 与 GRPO？** 前者对保留答案做监督模仿；后者从当前策略同题多次采样的相对奖励构造策略梯度，失败样本也参与相对比较。
3. **group 怎么构成？** 同一个任务 prompt 下多条独立环境采样，不是把不同 Issue 随意凑组。
4. **为什么多条？** 比较同题不同策略行为并估计相对优势，同时增加执行成本；若全都一样差，增加数量也未必产生有用信号。
5. **优势怎么算？** 常见形式为 A_i=(r_i−组均值)/(组标准差+ε)，不训练独立 value model；实际归一化和 loss 以固定 TRL 版本/config 为准。小组方差估计不稳定是代价。
6. **全部失败？** 若奖励相同，奖励导向优势为零；先区分环境错误、协议错误与真实语义失败，改数据/动作支持或选择可学课程。不能凭空给随机奖励造梯度。
7. **全部成功？** 若奖励相同，同样无组内质量区分，可换更难任务；不等于当前策略不好，也不等于包含 KL 等项的总目标必然零梯度。
8. **终局奖励如何作用于长轨迹？** 将轨迹优势作用于策略生成 token 的 log probability；这不是逐动作的精确因果归因，长链信用分配仍然困难。
9. **observation 算 loss？** 环境返回是条件信息，不应当成策略生成 token 优化。SFT 明确 completion-only；GRPO 使用 TRL 工具/环境接口的 masking，答细节前以所用版本实际 mask 审计为准，不能把 SFT 的审计结果直接当 GRPO 审计。
10. **GRPO 后一定 RS-SFT？** 不需要；它是可比较的后续策略，可能蒸馏成功行为，也可能改变分布或丢失探索，需独立实验。本项目没验证该组合。

### 奖励：六个问题

1. **为什么不能只用 0/1？** 可以用，且易解释；问题是当前成功稀疏导致组内同分。部分奖励是本项目尝试，并非理论必需。
2. **F2P/P2P 权重怎么定？** 不捏造调参结论。当前做法是先限制新增失败，再给失败减少部分分；系数未经足够消融，最终仍以严格通过判断。
3. **防删除测试或伪造成功？** 受限工具、保护 verifier-owned 文件、由环境执行实际测试而非读取模型自报；这减少直接篡改，不证明能杜绝针对可见测试的硬编码或所有漏洞。
4. **学习型 verifier 能作唯一奖励吗？** 可能误判且被利用，若有可执行测试应保留锚点；我们没有训练这种模型，使用测试验证器。
5. **怎么识别走捷径？** 同看 shaped reward、严格成功、原始测试输出、失败标识、补丁、违规率及固定预算对照。我们实际发现编辑分增加却不修复。
6. **行为惩罚会提前退出吗？** 可能，因此不要让节省步骤抵消完成任务的收益。当前主奖励没有验证过有效的连续 loop penalty；循环保护主要是执行层约束，不冒充奖励消融成果。

### 学习型 Verifier：八个问题（扩展知识，非本项目成果）

1. **输入 patch 还是轨迹？** 都可设计：patch 成本低，轨迹包含定位与测试过程但更长，也更容易依赖偶然提示。应按实际可用信息和泄漏边界选。
2. **成功概率怎么算？** 用执行标签训练分类/排序，再在独立集合校准；分类分数或 sigmoid 输出不自动等于校准概率。
3. **Pass@K 与 Best@K？** 先定义口径：Pass@K 是 K 个候选至少一个通过的概率/估计，Best@K 通常指排序器从 K 个候选选一个后的成功率。我们没做 Best@K 实验。
4. **为什么 Pass@K 通常不低于 Best@K？** 相同候选池下，至少存在一个正确候选是理想选择上限；排序器可能选错。不同样本、预算或估计方法不能直接套这个比较。
5. **选错怎么办？** 分开统计候选覆盖不足与“有正确候选却错选”，补针对性负例、改排序/校准或加执行检验。
6. **on/off-policy 为什么混合？** 当前策略样本贴近部署分布，历史样本扩大覆盖；比例需验证，旧数据分布偏移可能伤害效果。
7. **负样本过多？** 类不平衡可使模型偏向判失败；需看召回、排序与校准，并考虑采样/加权，而非只看 accuracy。
8. **能共享 reward model 吗？** 可以探索，但训练期与推理期输入和分布可能不同，作为优化目标还会产生被利用风险；必须独立评估，不是本项目已完成方案。

### 评测与工程：八个问题

1. **证明是 GRPO 而非更多 rollout？** 比较冻结策略，同任务、工具、token/步数/测试预算、采样数量和解码设置；多候选排序实验另列。本项目做了小规模方向对照，没有证明 RL 增益。
2. **为什么看 Pass@1？** 更接近单次策略质量；多采样可能提高候选覆盖而不改变单次能力。固定重复采样可估计成功概率，但当前小样本不应夸大精度。
3. **超时、Docker 崩溃、补丁失败？** 分类保存并定义分母；测试超时终止 episode，普通编辑错误作为 observation 可恢复，安全越界立即终止。
4. **怎样公平预算？** 固定步数、context、输出、测试次数/超时、候选数；另报实际 tokens 与耗时。不同硬件上的耗时不直接解释为算法提升。
5. **为什么 rollout 是瓶颈？** 每条多轮轨迹包含模型生成、工具执行、仓库/容器准备和真实测试，训练参数计算仅是其中一部分。不能在没有 profiling 的情况下报加速比例。
6. **如何并行 Docker？** 设计上可用独立会话、并发上限、资源配额、缓存与清理；本项目实现 provider/remote session，不声称已完成高吞吐集群调度优化。
7. **单位成本解决率？** 预先定义，例如成功任务数/总 GPU 小时，或总费用/成功任务数，说明是否含环境成本；零成功时每个成功任务成本不可用，不能写成 0 元。当前没有经过审计的成本下降结果。
8. **最典型 badcase？** 首选故事 A，再按岗位展开故事 B 或 C。每个故事都要说清原问题、证据、改动、结果与仍未解决部分。

## 7. 关于最近进度：怎么结束无止境补实验

当前不是完全没有产出，而是“可运行系统越来越完整，修复效果仍未突破”。继续给同一个任务追加样本、换 checkpoint，很容易积累更多记录，却不改变简历最缺的证据。现在可以把求职和实验拆开，不把面试启动绑定在 RL 最终成功上。

建议本轮收尾仅做四件事：

1. 使用上面的简历条目，删去未实现技术栈和效果占位符。
2. 准备一个已有轨迹的离线演示：Issue→工具调用→补丁→测试→reward audit。reference/教师示范必须显式标注，不能伪装模型成功案例。
3. 熟练讲三个故事，每个两分钟；能打开对应代码与报告解释指标含义。
4. 修正 README 与路线图的时间滞后，让 9 月 17 日停止结论、9 月 18 日待执行计划和早期机制验证清楚分开。

不需要为了让技术栈更长临时增加学习型 verifier、OpenHands 或再启动一轮训练。若以后继续投入，最有辨别力的是已有计划中的干净底座/adapter/教师正对照及多题留出编辑诊断，而不是承诺下一轮必然有提升；它们也不应成为开始投递的前置条件。

## 六处具体修改及理由

### 1. 项目名从“实验过程”转向交付物

原表述：基于 SWE-Gym 的代码修复 Agent 训练与可执行评测系统。

新表述：面向仓库级代码修复的 Agentic RL 训练与评测系统。

理由：先交代解决的问题和技术方向，数据集作为实现依据放到面试中。使用“系统”指已实现的训练评测组件，不暗示商业上线或集群规模。

### 2. 第一条不以“10 个任务”开场

原表述：在 10 个固定任务上划分 6/2/2 集合。

新表述：公开任务与私有验证配置分离，GPU 与 Docker 验证端跨主机交互。

理由：这条需要展示系统设计，任务数对这项能力说明有限。实验规模不占第一条，但问到时仍准确回答 10 个固定 Moto 任务、6/2/2 内部分组。

### 3. 训练条目采用“约束—方法—可确认结果”

原表述：完成 SFT/GRPO 机制验证。

新表述：构建动作监督、接入训练、解耦生成组与 microbatch，解决 OOM并完成非零梯度单步更新。

理由：把含糊的“跑通”展开成具体工程问题。保留“单步”是定义结果范围；不能将其压缩成“提升 Agent 修复能力”。

### 4. 奖励条目体现设计判断

原表述：奖励增加了，但成功率没有提高，所以停止实验。

新表述：通过配对实验识别代理奖励偏差，设计回归约束的版本化奖励。

理由：简历展示从证据到方案的技术判断，面试再解释负结果。使用“限制部分奖励”而非“消除 reward hacking”，因为只验证了已知规则缺口。

### 5. 排错记录升级为有边界的诊断方法

原表述：进行了导航、固定状态及局部编辑实验。

新表述：建立分层行为诊断，区分文件定位、动作协议、编辑执行和语义修复瓶颈。

理由：呈现这些实验共同回答的问题，避免像脚本清单。不能宣称已彻底确定根因；干净底座与教师后缀配对尚缺完成证据。

### 6. 把数字留给能解释贡献的地方

保留：204 条动作监督、32 条配对 rollout。它们分别说明数据构建交付与奖励设计的实验依据。

备查：10 个任务、6/2/2 划分、单题导航 4/8、curriculum 1/4、各轮零成功以及梯度/NLL 细节。

不加入：上游数据集总量作为本人实验量、SWE-Bench 成绩、成本降低比例或 Best@K。没有经核查的同口径数据，不创造结果。

>
> 系统上，我实现了 GPU 训练端与 Docker 验证端的跨主机交互，模型通过受限工具完成检索、编辑和测试，每次执行有独立环境和可恢复轨迹。训练上，我构建了工具动作监督数据，接入 LoRA SFT 和 GRPO，并通过生成组与 microbatch 解耦处理单卡显存问题，完成真实任务有效单步更新。

口头不要逐条念技术栈。先讲系统解决什么，再选一个技术问题深讲。首轮无需罗列全部失败记录；一旦被问“最终成功率提升多少”，直接回答结果。

## 四条简历对应的面试准备

### 训练与执行架构

主问：为什么拆开 GPU 和 Docker worker？

追问：私有测试配置怎么隔离？为什么不用现成 Agent 框架？网络或 worker 断开怎么办？

考察：能否解释组件边界与资源约束，而非只会调用模型 API。

回答结构：模型服务与仓库执行各自需要什么资源→provider/remote session 怎样对接→哪些字段能给 policy→轨迹和恢复如何保持一致。

证据：README、providers.py、docker_environment.py、grpo_remote.py、rollout.py。

范围：跨主机训练实验，不是分布式多机参数训练；无集群吞吐优化结论。

### 策略训练与显存优化

主问：OOM 出现在哪里，为什么改 microbatch 有用？

追问：组大小为何保持不变？204 条是什么单位？如何证明不是零梯度空跑？

考察：是否理解生成采样、组内优势和反向传播显存的区别。

回答结构：真实任务 backward OOM→保留两条生成构成组→训练 microbatch 从2降1→运行结束且不再OOM；有效更新另由后续组内奖励差异、非零梯度和 adapter 记录支持。

证据：README、grpo_train.py、swe_gym_sft.py、sft_train.py。

范围：204 条是 hunk 派生动作监督，不是204个Issue；微批调整解决本次OOM，不代表有吞吐提升或显存降低百分比数据。首次不OOM运行仍为零梯度，后续有效更新不要混成同一次实验。

### 执行反馈奖励

主问：原来奖励哪里出了问题？

追问：为什么不直接使用0/1？如何判断新失败？新奖励提高成功率了吗？

考察：是否能从代理指标偏差推导设计约束。

回答结构：旧奖励为有效编辑且主动测试给分→32条配对轨迹里编辑数量增加但测试未改善→新规则要求结果可比较、无新增失败，未知状态拒绝部分分→后续验证回归补丁不再得到该类奖励。

证据：reward_shaping.py、adapter-direction-check-20260913.md、train-failure-reduction-search-20260914.md。

范围：已修正规则缺口，尚未证明端到端成功率提升；不是训练出来的神经网络 verifier。

### 可复现评测与诊断

主问：loss 下降为什么还失败，怎样排查？

追问：训练与推理模板一致吗？如何区分导航和编辑？中间一步不改善测试就一定错吗？

考察：是否理解 teacher forcing、自由生成与多步执行的差异。

回答结构：检查schema、模板、mask和截断→导航到达率→固定状态重放→动作可解析/可应用→完整verifier；用最近NLL下降但训练状态仍0/3作为实例。

证据：moto-7607-diagnostic-v2-execution-20260917.md、moto-7607-local-edit-diagnostic-execution-20260917.md。

范围：中间编辑可能依赖后续动作；7个状态无立即改善不能独立证明所有编辑语义错误，教师后缀正对照仍待完成。

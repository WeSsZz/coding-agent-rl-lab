# Agent 训练 / 算法工程：项目简历与逐部分讲法

适用范围：项目片段与面试备稿，不是完整个人简历。依据本地代码、截至 2026-09-18 的执行记录及用户提供的五张参考截图；截图只提供选材结构，不证明本项目完成了其中的实验。本轮未重新运行远端训练。事实映射见 claim-ledger-20260919.json。

## 一、求职定位

项目当前最有支撑的定位是：面向真实仓库代码修复，构建执行反馈驱动的 Agent 训练与评测闭环，并用受控实验分析监督学习、策略更新与实际修复行为之间的差距。

对 Agent 训练 / 算法工程岗位，优先讲数据、训练、奖励和实验判断。环境工程作为这些实验能够可靠执行的基础。对于要求成熟大规模后训练和明确 benchmark 增益的岗位，当前项目证据仍有差距，不通过增加术语掩盖。

## 二、可直接用于简历的项目片段

**面向仓库级代码修复的 Agent 训练与执行反馈优化**

技术栈：Python、PyTorch、Transformers、TRL、PEFT/LoRA、Qwen2.5-Coder、Docker、vLLM（推理）

面向真实 GitHub Issue 修复，构建检索、编辑、测试与策略更新闭环，探索执行反馈驱动的多轮工具策略训练。

- **监督数据与策略训练：**从训练集源码补丁构建 204 条定位、读取、编辑和验证动作监督样本，接入 completion-only LoRA SFT 与多轮环境 GRPO；解耦生成组与训练 microbatch，解决单卡反向传播 OOM，并在后续实验中完成真实任务非零梯度的单步策略更新。
- **执行反馈奖励：**通过 32 条同任务、同种子与同预算的配对 rollout，识别有效编辑奖励与测试改善不一致的问题；实现基于失败测试集合和回归约束的版本化奖励，拒绝为新增失败及未知测试状态提供部分奖励。
- **行为评测与诊断：**建立导航、工具协议、固定状态与局部编辑分层诊断；引入教师后缀正对照，修正仅凭即时测试改善判断中间编辑的口径，区分工具格式改善与语义修复能力。
- **训练执行系统：**实现 GPU 训练端与 Docker 验证端的跨主机协同，隔离 policy 可见任务与私有答案配置，支持测试文件保护、完整交互轨迹、原子检查点与配置一致性校验后的断点恢复。

选材映射：第一条 C03–C06；第二条 C07–C08；第三条 C09–C11；第四条 C01–C02 及 README 的跨主机架构记录。限定为项目实现贡献，不附加团队负责人、商业上线或独立完成全部工作的归因。简历中不必列每轮失败数字；被问到效果时直接说明没有证明完整任务修复率提升。

## 三、参考截图逐部分如何吸收

### 1. 项目名称与主线

吸收“任务—数据—训练—反馈—评估”的组织方法。我们的主线是 SFT warm-start → 执行反馈 GRPO → 配对评测与失败诊断。尚未形成“拒绝采样迭代 → 学习式 Verifier → Best-of-N 提升”的已验证链条。

开场解释：项目研究的不只是生成一段代码，而是模型在仓库里通过多轮检索、编辑和测试完成修复。训练数据、工具协议和执行奖励必须对齐，才能判断参数更新有没有转成有效行为。

### 2. 数据部分

推荐讲法：我采用 SWE-Gym 的真实任务与可执行环境，先固定 10 个 Moto 任务，划分 6 个 train、2 个 regression 和 2 个 held-out，用于小规模机制验证。训练监督来自 train-only 官方 gold patch：51 个源码 hunk 派生四阶段动作，共 204 条，不是 204 个 Issue，也不是 204 条模型自主成功轨迹。

价值：任务元数据、可执行验证配置和监督答案有不同的可见边界；reference/gold 路径只证明基础设施或提供明确标记的训练监督，不能混入无答案评测。

追问准备：解释 instance、hunk、action、trajectory 的单位；拿一条样本说明输入与监督目标；说明 split 如何拒绝越界数据。当前是同仓库任务级划分，不能宣称跨仓库泛化，也不能宣称已做 SWE-Bench 去污染审计。

截图中的 2,438、358→11 是上游数据构建背景，不是我们的采集或训练规模。面试中可介绍来源，但不能把它写成本人完成的数据工程。

### 3. 模型与 Agent 部分

推荐讲法：以 Qwen2.5-Coder-7B 为主要训练策略，使用自建受限工具 scaffold 执行搜索、读取、源码修改和测试；模型负责选择动作，环境执行动作并返回 observation。模型服务和 Docker worker 分开部署，便于分别处理 GPU 与仓库执行资源约束。

选择 7B 的可辩护依据是现有单卡训练资源和机制验证范围，不宣称经过全面模型选型证明最优。14B 出现在后续局部诊断中，不是已验证优胜的最终方案。不要把截图里的 7B/14B/32B 分工、OpenHands 或 SGLang 当成自己的实现。

自建 scaffold 的取舍：动作空间受限、便于审计、能精确控制实验变量；代价是工具协议适配与分布变化需要自行处理。不要泛称比现成框架更强。

### 4. SFT 与拒绝采样

推荐讲法：初期模型在真实任务上难以产生可用正反馈，因此用训练集 gold patch 构建动作监督 warm-start。completion-only loss 聚焦待预测动作；不能把环境返回的测试输出当成模型应该模仿生成的答案。

我们这条主要路径是 gold-derived SFT。拒绝采样 SFT 是从模型采样结果中按验证条件筛选成功样本再训练，两者数据来源不同。现有成功轨迹筛选能力不等于已经完成多轮拒绝采样训练及效果验证。

可讲的深度：训练 loss 下降不保证自由生成与多轮执行成功；9 月 17 日 NLL 从约 0.572 降至 0.291，三个训练状态仍没有严格成功。这是局部诊断结果，不能扩大为 SFT 无效。

### 5. GRPO 部分

推荐讲法：同一任务采样多条交互轨迹，使用最终执行反馈形成组内相对训练信号。项目接入 TRL 的环境训练接口，没有自行发明 GRPO。先解决 backward OOM，再解决真实任务组内奖励没有差异的问题。

两个问题分开讲：生成组保持为 2、训练 microbatch 降为 1 后，训练能结束，但当时 reward=[0,0]、梯度仍为零。随后受控行编辑恢复路径使模型能够产生补丁；后续 seed 的奖励为 [0,0.15]，grad_norm=0.4935，证明有效单步更新链路成立。

不把一次非零梯度写成“提升修复率”。全失败组或全成功组如果所有总奖励相同，组内任务奖励优势缺乏区分信号；这不自动证明任何配置下总梯度都为零，因为还要检查 KL 等损失项。项目是否有效更新以实际日志为准。

### 6. 奖励设计

推荐讲法：训练奖励与最终成功指标分离。严格成功依赖执行 verifier 全通过、有源码补丁、无违规。旧奖励为有效补丁并主动测试提供部分分；配对评测发现即使引入新增失败也可能得分，因此加入失败集合可比较与无新增失败约束。

具体案例：train 的有效补丁由 3/12 变成 5/12，但严格成功两组都是 0/12，识别到的新增失败由 1 条变为 2 条；不能把 reward 上涨解释为能力提高。这些是小样本观察，不声称统计显著。

conservative-v2 对新增失败、未知结果等不发部分奖励。对可比较、有效且无新增失败但未改善测试的补丁仍留 0.03，这只是待验证设计，不能说已完全消除奖励投机。当前代码也不是截图所述一整套已验证的循环惩罚、长度惩罚和 FTP/PTP 权重调优系统。

对“为什么不能用 0/1”先纠正前提：可以用，问题是当前采样常出现相同奖励、缺少有效区分。密集奖励提供额外信号，同时引入代理目标偏差，所以需要严格成功指标独立验收。

### 7. Verifier 部分

必须区分可执行 verifier 与学习式 Outcome Verifier。我们已经有前者：运行测试并读取真实结果；截图中的后者是训练模型给候选轨迹评分，再做排序。

推荐讲法：本项目以执行测试作为奖励和评测依据，尚未训练候选排序 verifier，也没有 Best-of-N 增益结论。后续若扩展，应先有足够多同题候选与可信标签，按任务划分数据，再比较随机选、评分选及候选中存在正确答案的上界。

理解题：同一批 K 个候选，“至少一个成功”的 oracle 事件包含“排序器选中的一个成功”事件，因此对应的 oracle success@K 不低于 selected success@K。Pass@K、Best@K 必须先约定统计定义，不能跨不同采样集合直接比较。

此部分用于展示理解与后续设计，不为了术语完整现在新增一个 verifier 项目。

### 8. 评测与工程

推荐讲法：比较 SFT 与 GRPO 时固定任务、种子和预算并冻结权重，保留报告、工具轨迹和版本。32 条是两种策略各 16 条，即 8 题×2 次×2 策略，不是 32 个独立任务，也不是 32 对。

运行失败、工具协议错误、补丁失败和未知测试状态要分开记录，不能挑掉失败样本后仍沿用原成功率口径。当前某些路径对基础设施或协议异常作零奖励并单独归类；不要声称已经完成所有基础设施失败的重试校正。具体汇报时同时给计划数、完成数和异常数。

相同 rollout 数并不自动等于相同总成本：还要核对 token、最大步数、测试超时与硬件。项目支持部分成本观测，但没有可用于简历的成本降低比例。

### 9. Badcase 与调优

重点准备三个真实故事，不背整张错误分类列表。

故事 A：精确替换失败。真实 GRPO smoke 的四次 replace_text 中，三次无精确匹配、一次参数错误，没有补丁。加入仅针对已读源码、限制行数且编辑后使行号失效的 replace_lines；后续轨迹能够形成补丁并运行测试。结论是改善了动作可执行性，没有证明语义修复成功。

故事 B：代理奖励偏差。有效补丁增多、奖励上涨，但测试不改善且出现新失败；据此修正奖励的准入条件。强调观察—解释—修改—验证边界。

故事 C：中间动作评估错位。7 个教师编辑当前立即验证只有 3 个成功，但接固定教师后缀后 7 个全成功，说明多处修改任务不能要求每一步立刻修复最终测试。再把模型动作替换进去执行相同后缀，adapter 的 4 个可应用动作均未成功，因此本轮不能将失败仅解释成“后续步骤没做完”。固定后缀是受控诊断，不能覆盖所有等价修复路径。

9 月 18 日干净底座动作可解析 0/7、adapter 4/7，两者后缀语义成功都为 0/7；特殊 token 退化也出现在底座中，不能把它一概归因于 adapter。七个状态来自同题，不是泛化 benchmark。

## 四、90 秒项目开场

> 这个项目面向真实仓库的 Issue 修复，核心是让模型通过检索、编辑和测试完成多轮任务，并用执行结果训练策略。
>
> 我重点做了三部分。首先是训练数据和执行闭环：从训练集源码补丁构建 204 条动作监督，接入 LoRA SFT 和环境交互式 GRPO，并让 GPU 训练端与 Docker 测试端协同运行。其次是在单卡约束下处理训练问题，通过生成组与训练微批解耦解决反向传播 OOM，后续完成了真实任务非零梯度的单步更新。
>
> 第三部分是验证更新有没有真正带来有效行为。32 条配对 rollout 表明，编辑奖励增加并没有带来测试改善，因此我加入回归约束，并把失败拆成导航、工具协议和语义编辑。最近还用教师后缀正对照发现，中间步骤不能只看即时测试改善。
>
> 当前完整任务评测还没有证明修复率提升。项目已经形成可复现的训练评测闭环，也积累了定位奖励偏差和行为瓶颈的方法。
